# Kiro account environment

Kiro requests use one persisted account environment: machine ID, Kiro version,
Node version, operating system version, authentication region and API region.
New imports receive defaults only for omitted values. Token-only credential
updates retain the environment, authentication method and profile binding;
explicit snake_case, camelCase or nested JSON values take precedence. Rotating
access tokens and per-request invocation IDs are not device identities.

Generation, model discovery, usage and token refresh share the operation header
builder in `internal/pkg/kiro/profile.go`. Each operation keeps its required SDK
identity and authentication scheme. The IDE generation/usage origin is
`AI_EDITOR`; the management model catalog retains its existing `KIRO_CLI`
origin. These are operation-specific protocol fields, not a rotating machine ID.

All four operations use the Kiro upstream profile: HTTP/1.1, Connection: close,
no redirects and account-isolated clients. Existing dedicated static proxy
validation remains mandatory, including refusal of direct/backup fallback.
Model and completed-response cache keys include the effective environment hash.
Usage caches already include the complete credential and proxy identity.

The account action menu's fingerprint view renders a credential-free allowlist
from the same builder used by requests. It shows the machine/environment,
regions, bound proxy ID, operation endpoints and stable headers. Bearer tokens,
client secrets, proxy credentials, profile ARNs and invocation IDs are excluded.

## Compatibility boundaries

The persisted account environment follows the pinned `hank9999/kiro.rs` reference
revision `8fb3dd691d1cedf437bd6a4e9ef9f60b3f217fdd`. Generation uses the
`KiroRuntimeService.GenerateAssistantResponse` AWS JSON operation at
`https://runtime.{region}.kiro.dev/`, with the matching `kiroruntime` SDK identity.
The operation was cross-checked against `yupanzi/kiro2claude` revision
`990bf02489fe6b6a7dbca299f737c5b382c6a4d9` and verified with live requests. SDK attempt metadata describes this
implementation's single attempt (`attempt=1; max=1`); it does not claim the
reference's multi-attempt policy. HTTP Host, Content-Length and negotiated
compression are generated by Go's transport rather than client-supplied values.

TLS currently uses Go crypto/tls. No native Kiro ClientHello capture has verified
cipher suites, extension order, JA3/JA4, TCP signatures or HTTP header order.
This implementation must not be described as a complete native TLS clone.
Kiro's implemented upstream protocol is HTTP eventstream; there is no Kiro
WebSocket transport.

The runtime operation preserves terminal metadata that the older CodeWhisperer
endpoint omitted. The original full-context CLI reproduction returned explicit
`CONTENT_FILTERED` metadata, with a `CYBER` refusal category. The adapter maps
explicit filtering to `400 kiro_content_filtered` (or an in-stream error after
headers are committed), without successful completion, cache admission or billing
for an empty rejected response. Context-only responses without a reason remain
`502 kiro_empty_response`; they are never labeled as filtering by inference.
No prompt rewriting, model substitution or account failover is performed to
work around an upstream refusal. Account identity consistency does not disable
provider content rules.
