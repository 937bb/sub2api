## 2. Craft-floor assessment

**Coverage fails.** The inventory exposes whole overlay families that did not join the redesign. `AnnouncementPopup.vue` still has a dark gradient scrim, decorative blur circles, orange gradient header/button, oversized title, animated unread decoration, and a thick colored content rail. `TotpStepUpDialog.vue`, TOTP login/setup/disable, passkey deletion, redemption generation/results, backup guides, settings subdialogs, payment renewal, announcement reading, and several image viewers use handwritten structures. Updating only `BaseDialog` cannot reach them.

**Spacing and hierarchy fail in the concrete creation flow.** `before-user-create.png` shows a full-height 880px sheet with a large empty label column, almost every field separated like a settings table, and one inconsistent two-column balance/concurrency row. `workbench.css:157` forces every opted-in sheet to `min(880px, 100vw)`, regardless of `width="narrow"` or `width="normal"`. Lines 162–165 impose per-child borders and a `160px` label column. This makes a short creation task visually expansive while giving no semantic grouping to identity, access, and limits.

**The browser-surface treatment is incomplete across portals.** `BaseDialog.vue:2` teleports to `body`. Compact button/input/select rules, numeric inheritance, caret styling, selection styling, and the shared focus rules in `console.css` predominantly target descendants of `.console-shell`; body-mounted content is outside that subtree. Root variables reach portals, and global `.input` rules still apply, but those facts do not make all console component rules apply. The few `body:has(.console-shell) .modal-*` selectors cover only the wrapper, title, and footer. This is a concrete cascade gap, not a claim that every portal has no styling.

**Depth and decoration are inconsistent.** The shared dialog has a restrained soft shadow and unblurred 32% scrim, but custom overlays keep 50–80% masks, blur, rings, gradients, and unrelated corner sizes. The pinned New API source uses its own light backdrop and restrained overlay anatomy; its small backdrop blur is reference evidence and is not categorically forbidden by the craft floor. Remove unsupported decorative effects, not reference-earned treatments.

**States and accessibility are not certified.** The incumbent base preserves topmost-base Escape behavior, scroll locking, and focus restoration, but it has no Tab focus containment and handwritten overlays do not participate in its open-dialog registry. User-create labels are not associated with controls by `for`/`id`, and the close label is hard-coded English in the reviewed commit. Contrast, mobile keyboard overlap, nested popup focus, loading/error layouts, and long translated content require rendered checks after implementation. Do not count screenshot cleanliness as a pass for these states.

## 4. Functional risks and preservation constraints

- **Nested verification:** user creation calls `stepUp.run()` and may open TOTP above a still-open form. Preserve automatic retry, cancellation leaving the original form open, entered values, and verification loading behavior. A new focus trap must allow the active nested overlay and teleported selectors; a naïve trap around only the base panel can make them unusable.
- **Dismissal and stacking:** preserve `closeOnEscape`, outside-click policy, close-button visibility, caller z-index, topmost-only dismissal, body lock reference counting, and return focus. Handwritten verification/announcement overlays currently fall outside the base registry, so changing one family alone can close the underlying task or release scroll too early.
- **Form submission and precision:** retain detached footer `form` attributes, submit handlers, HTML validation, conditional sections, disabled states, password generation, blank-versus-zero balance behavior, `rpm_limit=0` semantics, and numeric precision. New API's fields, role numbers, quotas, API payloads, and permission matrix must not replace Sub2API's data model.
- **Complex editors:** accounts, keys, groups, proxies, subscriptions, monitors, TLS profiles, error passthrough rules, plans, and prompt-audit pools contain provider-specific or conditional controls. Keep every existing field, tab, disclosure, custom option renderer, validation path, import/export action, and nested editor. Do not flatten everything into one indistinguishable form just to obtain uniform CSS.
- **Investigations and finance:** retain request IDs, routing/provider details, error payloads, timings, token categories, account/customer/standard cost distinctions, refunds, currencies, and fee calculations. Preserve safe wrapping and local overflow for JSON, logs, keys, tables, and long identifiers.
- **Other overlay families:** announcement rendering/sanitization and read state, payment polling/cancellation, provider-owned checkout, image zoom/download, passkey/OTP behavior, export progress cancellation, and selection search/keyboard navigation must survive the visual migration. Retain genuine payment-provider marks.
- **Scope:** UI presentation only. Preserve permissions, flags, routes, stored theme, branding, locales, backend endpoints, persistence, and deployment boundaries. This review does not authorize backend changes, new product fields, or deployment C changes.

## 5. Prioritized concrete fixes and acceptance scope

1. **P1 — Establish real overlay primitives and make their interior controls work in portals.** Give dialogs, editor drawers, confirmations, and anchored popovers explicit anatomy, size roles, header/description support, body scrolling, footer layout, motion, and tokens. Apply control typography, focus, caret, selection, and numeric rules to the overlay root rather than relying on shell ancestry. Short confirmations and balance adjustments must not become 880px sheets. Acceptance: base width choices remain effective, and equal controls look the same inside the page, drawer, dialog, and teleported dropdown in light/dark modes.

2. **P1 — Rebuild the editor interiors, starting with the screenshot the user rejected.** For user create/edit, adopt the observed approximately 600px user-drawer composition: vertical labels, a concise explanatory header, meaningful identity/access/limit sections, 16px field spacing, section-level dividers, and a fixed footer. Keep Sub2API's email/password/username/role/balance/concurrency/RPM behavior. Then apply the same family to account, key, group, channel, proxy, subscription, plan, announcement, monitor, import, bulk-edit, TLS, and error-rule editors, choosing wider layouts only for actual dense content. Acceptance: template composition visibly changes; changing only `presentation`, border radius, or global descendant selectors is insufficient.

3. **P1 — Close every handwritten-overlay gap.** Use the 110-file inventory as a coverage ledger, with each occurrence marked migrated, intentionally retained as an image/provider surface with the shared chrome, or an anchored popover receiving its own component treatment. Explicitly include security prompts, passkey deletion, announcements and their reader, redemption generation/batch/results, subscription and backup guides, payment renewal, settings subdialogs, account test image viewers, and menus/tooltips. Acceptance: no forgotten gradient announcement or old TOTP screen remains after the main editor looks finished; no active feature is hidden or deleted to reduce the inventory.

4. **P1 — Compose dense details and confirmations as their own families.** Request/error/audit/order/monitor details need compact summary plus labeled sections, dedicated code/data viewers, and predictable action placement. Confirmations need the shared compact alert treatment, destructive semantics, and pending protection where the caller already exposes async state. Preserve actual content and all existing actions. Acceptance: users can identify the object/action, inspect all underlying data, and complete or cancel without layout jumps, duplicate submissions, or lost state.

5. **P2 — Verify completeness with a bounded, representative state matrix and a full source ledger.** One batched desktop/mobile inspection should include: create and edit user; nested administrator TOTP; balance adjustment; complex account/group/key editor; destructive confirmation; usage/error detail; a custom redemption or settings dialog; announcement list/detail/popup; payment/QR/provider boundary; searchable select and row-action popover. Include dark theme, English/Chinese long labels, loading/error/disabled states, keyboard Tab/Shift-Tab/Escape, a narrow viewport with software-keyboard constraints, and long data. Inspect the complete inventory statically, not only those screenshots. Fix the findings once, then make one confirmation pass. Acceptance: document which families and states were directly exercised; do not claim all dialogs were tested from a handful of captures.

Revision 8 is ready for user review only when the full inventory has a disposition, the required user-create screenshot demonstrates the structural replacement, all overlay families share the reference's component language, and the preservation checks remain intact. A new shell screenshot alone cannot satisfy this rejection.
