# Sub2API 0.2.4.1

Both `937sub` and `937sub2b` merge official `v0.2.4`, including version-sync
commit `98d86915`. Custom versions use the official version plus `.1`.

The B branch preserves the deployed 0.2.3.1 fixes, quota expansion and 429
recovery, OAuth/PAT WebSocket handling, IPv6 routing, account identities and
privacy records. The six OAuth retry and operations-log commits from the second
fork are merged rather than overwritten. Their retry toggle remains unchanged.
The C branch retains growth, subscription, payment, and time-billing features.

Official changes include transient-429 cooldown handling, HTTP/2 keepalive,
client-disconnect draining, MiniMax support, proxy backup handling and Image 2.5.
The WS result now also preserves requested reasoning effort when draining a
disconnected client; the cancellation regression test checks this field.

## Validation

Both default Go suites and frontend builds pass. The frontend suite required
updating provider-count expectations after adding MiniMax, plus C manifest-test
fixtures. Targeted repository integration tests exercise migration compatibility,
fingerprint backfill, and directed/repeated proxy fallback. `go vet` passes.

C golangci-lint reports no issues. B retains 14 previously documented findings:
one service-layer Redis dependency, eight test error checks, one test formatting
issue and four unused declarations. The three new close-error findings from the
second fork are resolved. The separate legacy `unit` build-tag suite is not
claimed as passing.

## Rolling deployment

Primary listeners remain B `6064` and C `26063`; C upstream URLs remain
`http://127.0.0.1:6064`. Candidate listeners are B `36064` and C `36063`.
Retain current and prior hashed frontend assets in the embedded release so
existing browser sessions can load lazy chunks after cutover.

Before starting C beside its old version, keep both `models_list_config` and
`model_allowlist` with the existing bidirectional compatibility trigger. Apply
pending official SQL unchanged with the migration advisory lock, a one-second
lock timeout, and an eight-second statement timeout. Do not remove compatibility
columns during this release. Migration identity uses the complete filename,
so the independent migration files numbered 237 remain distinct and immutable.

Validate candidate pages, assets, administrator reads and inference before
routing new local-port connections. Keep established and half-closed streams
on their old listener until they finish. Only recreate the corresponding
Compose service after it drains; keep candidate routing until the new primary
is healthy. Never use `docker compose down`, stop an active listener, restore
the database, or modify CPA/CPAMP during this deployment.

Root-only release records are under each deployment's `releases/0.2.4.1`.
Release-specific finalizer timers complete draining without a forced deadline.
Before a later release, inspect their state and exact expected images. For
rollback while the original primary is running, disable the finalizer and
remove only this release's new-connection redirect. After primary replacement,
first route to a healthy compatible candidate, drain the primary, then restore
its protected Compose snapshot. Keep the compatibility schema for rollback.

## Production verification, September 10

Both domains and original local ports now route new connections to 0.2.4.1.
The B binary is built from `635f9a4f`; the C binary from `9b3ee789`.
The original listeners remain until their established connections drain.
The release-specific finalizers, not a forced deadline, perform replacement and
remove the temporary candidates. Inspect `completed.json` and the timers before
starting another release.

All 416 B assets and 289 C assets match their embedded release hashes, including
retained assets from earlier builds. Both domain pairs return the expected
frontend entry resources. Administrator version, account, and group reads pass.
B native WS and C-to-B HTTP streaming completed real model responses. Pro HTTP
smoke requests also encountered upstream 429/overload; the same-key old-listener
control returned the same 429 and logged model-limited upstream accounts. These
upstream failures must not be reported as universally resolved by the merge.
Account fingerprints and training opt-out records for common account IDs, group
configuration, and database settings match the pre-deployment snapshots.

The server PostgreSQL limit is 100 client connections. Existing B/C pool limits
were 128/256, and a parallel candidate initially exhausted available slots.
That unrouted candidate was stopped. Fourteen old B database connections idle
for at least 78 seconds, outside transactions, were retired after matching
their source ports to the old B process. HTTP/WS client sockets were retained.
Candidates use eight database connections; replacement primaries are configured
for 32 open and eight idle connections each. Account/inference concurrency is
unchanged. Database changes are limited to the documented additive migrations;
the PostgreSQL server and other projects were not restarted or reconfigured.

Root-only rollout scripts and detailed records are in
`/var/tmp/sub2api-v024-20260910` and each service's `releases/0.2.4.1` directory.
The first Python HTTP monitor was rejected by the C CDN while curl returned 200;
the subsequent curl-based domain/local-port monitoring is the valid cutover
record. Do not combine that client-specific 403 baseline with application
availability or claim that every inference succeeded.
